A01:2021 – Broken Access Control

설명

접근 제어는 사용자가 의도된 권한 외의 작업을 수행할 수 없도록 정책을 시행합니다. 실패는 일반적으로 모든 데이터의 무단 정보 공개, 수정 또는 파괴 또는 사용자의 제한 내에서 비즈니스 기능을 수행하는 것으로 이어집니다. 일반적인 접근 제어 취약점에는 다음이 포함됩니다:

  • 최소 권한 원칙 또는 기본 거부 위반, 특정 기능, 역할 또는 사용자에게만 액세스가 부여되어야 하지만 누구나 사용할 수 있습니다.
  • URL 수정(매개변수 변조 또는 강제 탐색), 내부 애플리케이션 상태 또는 HTML 페이지에 의한 접근 제어 검사 우회, 또는 API 요청을 수정하는 공격 도구 사용.
  • 고유 식별자를 제공하여 다른 사람의 계정을 보고 또는 편집할 수 있도록 허용(안전하지 않은 직접 객체 참조).
  • POST, PUT 및 DELETE에 대한 누락된 접근 제어로 API 액세스.
  • 권한 상승. 로그인하지 않고 사용자 역할을 하거나 사용자 로그인 시 관리자 역할을 함.
  • JWT 액세스 제어 토큰 재생 또는 변조, 권한 상승을 위한 쿠키 또는 숨겨진 필드 조작 또는 JWT 무효화 남용과 같은 메타데이터 조작.
  • CORS 잘못 구성으로 승인되지 않은/신뢰할 수 없는 출처에서 API 액세스 허용.
  • 인증되지 않은 사용자로 인증된 페이지 또는 표준 사용자로 권한 있는 페이지 강제 탐색.

예방 방법

접근 제어는 공격자가 접근 제어 검사 또는 메타데이터를 수정할 수 없는 신뢰할 수 있는 서버 측 코드 또는 서버리스 API에서만 효과적입니다.

  • 공개 리소스를 제외하고 기본 거부.
  • Cross-Origin Resource Sharing (CORS) 사용 최소화를 포함하여 애플리케이션 전체에서 접근 제어 메커니즘을 한 번 구현하고 재사용.
  • 접근 제어 모델은 사용자가 모든 레코드를 생성, 읽기, 업데이트 또는 삭제할 수 있다고 받아들이는 대신 레코드 소유권을 시행해야 합니다.
  • 고유한 애플리케이션 비즈니스 제한 요구 사항은 도메인 모델에 의해 시행되어야 합니다.
  • 웹 서버 디렉터리 목록을 비활성화하고 파일 메타데이터(예: .git) 및 백업 파일이 웹 루트 내에 존재하지 않도록 합니다.
  • 접근 제어 실패를 로그하고 적절한 경우 관리자에게 경고(예: 반복 실패).
  • 자동화된 공격 도구로부터의 피해를 최소화하기 위해 API 및 컨트롤러 액세스를 속도 제한.
  • 상태 저장 세션 식별자는 로그아웃 후 서버에서 무효화되어야 합니다. 상태 비저장 JWT 토큰은 공격자의 기회 창을 최소화하기 위해 오히려 단기간이어야 합니다. 더 긴 기간의 JWT의 경우 OAuth 표준을 따라 액세스를 취소하는 것이 적극 권장됩니다.

개발자와 QA 직원은 기능적 접근 제어 단위 및 통합 테스트를 포함해야 합니다.

공격 시나리오

시나리오 #1: 애플리케이션이 계정 정보에 액세스하는 SQL 호출에서 검증되지 않은 데이터를 사용합니다:

pstmt.setString(1, request.getParameter("acct"));
ResultSet results = pstmt.executeQuery( );

공격자는 브라우저의 'acct' 매개변수를 수정하여 원하는 계정 번호를 보냅니다. 올바르게 검증되지 않으면 공격자는 모든 사용자의 계정에 액세스할 수 있습니다.

https://example.com/app/accountInfo?acct=notmyacct

시나리오 #2: 공격자는 단순히 대상 URL을 강제 탐색합니다. 관리자 페이지 액세스에는 관리자 권한이 필요합니다.

https://example.com/app/getappInfo
https://example.com/app/admin_getappInfo

인증되지 않은 사용자가 어느 페이지에 액세스할 수 있다면 결함입니다. 비관리자가 관리자 페이지에 액세스할 수 있다면 결함입니다.

A02:2021 – Cryptographic Failures

설명

전송 중인 데이터와 저장된 데이터의 보호 필요성을 먼저 파악해야 합니다. 비밀번호, 신용카드 번호, 건강 기록, 개인 정보 등은 특별한 보호가 필요합니다. 일반적인 문제로는 평문으로 전송되는 데이터, 오래되거나 약한 암호화 알고리즘 사용, 기본값 또는 약한 암호화 키 사용, 암호화 미실행, 서버 인증서 검증 부재, 초기화 벡터 오류, 약한 해시 함수(MD5, SHA1) 사용, 비암호화 패딩 방법 사용, 암호화 오류 메시지 노출 등이 포함됩니다.

  • 데이터가 평문으로 전송되나요? HTTP, SMTP, FTP와 같은 프로토콜과 STARTTLS와 같은 TLS 업그레이드를 사용하는 것이 이에 해당합니다. 외부 인터넷 트래픽은 위험합니다. 로드 밸런서, 웹 서버 또는 백엔드 시스템 간의 모든 내부 트래픽을 확인합니다.
  • 기본값 또는 이전 코드에서 오래되거나 약한 암호화 알고리즘 또는 프로토콜이 사용되나요?
  • 기본 암호화 키가 사용되거나, 약한 암호화 키가 생성 또는 재사용되거나, 적절한 키 관리 또는 회전이 누락되나요? 암호화 키가 소스 코드 저장소에 체크인되나요?
  • 암호화가 시행되지 않나요? 예를 들어, HTTP 헤더(브라우저) 보안 지시문 또는 헤더가 누락되나요?
  • 받은 서버 인증서와 신뢰 체인이 적절하게 검증되나요?
  • 초기화 벡터가 무시되거나 재사용되거나 암호화 모드 작업에 충분히 안전하게 생성되지 않나요? ECB와 같은 안전하지 않은 작업 모드가 사용되나요? 인증된 암호화가 더 적절할 때 암호화가 사용되나요?
  • 비밀번호 기반 키 파생 함수가 없는 경우 비밀번호가 암호화 키로 사용되나요?
  • 암호화 목적으로 설계되지 않은 무작위성이 사용되나요? 올바른 함수가 선택되더라도 개발자가 시드해야 하며, 그렇지 않은 경우 개발자가 내장된 강력한 시드 기능을 충분한 엔트로피/예측 불가능성이 부족한 시드로 덮어썼나요?
  • MD5 또는 SHA1과 같은 폐기된 해시 함수가 사용되거나, 암호화 해시 함수가 필요할 때 비암호화 해시 함수가 사용되나요?
  • PKCS 번호 1 v1.5와 같은 폐기된 암호화 패딩 방법이 사용되나요?
  • 패딩 오라클 공격 형태의 암호화 오류 메시지 또는 사이드 채널 정보가 악용될 수 있나요?

예방 방법

다음을 최소한으로 수행하고 참조를 참조하세요:

  • 애플리케이션에서 처리, 저장 또는 전송되는 데이터를 분류합니다. 개인 정보 보호법, 규제 요구 사항 또는 비즈니스 요구 사항에 따라 민감한 데이터를 식별합니다.
  • 불필요하게 민감한 데이터를 저장하지 마세요. 가능한 한 빨리 폐기하거나 PCI DSS 준수 토큰화 또는 절단을 사용하세요. 보유되지 않은 데이터는 도난될 수 없습니다.
  • 저장된 모든 민감한 데이터를 암호화하세요.
  • 최신의 강력한 표준 알고리즘, 프로토콜 및 키를 사용하고 적절한 키 관리를 사용하세요.
  • 전달 보안(FS) 암호, 서버의 암호 우선 순위 지정 및 보안 매개변수와 함께 TLS와 같은 보안 프로토콜로 전송 중인 모든 데이터를 암호화하세요. HTTP Strict Transport Security (HSTS)와 같은 지시문을 사용하여 암호화를 시행하세요.
  • 민감한 데이터를 포함하는 응답에 대한 캐싱을 비활성화하세요.
  • 데이터 분류에 따라 필요한 보안 제어를 적용하세요.
  • FTP 및 SMTP와 같은 레거시 프로토콜을 사용하여 민감한 데이터를 전송하지 마세요.
  • Argon2, scrypt, bcrypt 또는 PBKDF2와 같은 강력한 적응형 및 솔트 해시 함수를 사용하여 비밀번호를 저장하세요.
  • 초기화 벡터는 작업 모드에 적절하게 선택되어야 합니다. 많은 모드에서 이는 CSPRNG(암호화적으로 안전한 의사 난수 생성기)를 사용하는 것을 의미합니다. 논스가 필요한 모드의 경우 초기화 벡터(IV)는 CSPRNG가 필요하지 않습니다. 모든 경우에 IV는 고정 키에 대해 두 번 사용되어서는 안 됩니다.
  • 항상 암호화 대신 인증된 암호화를 사용하세요.
  • 키는 암호화적으로 무작위하게 생성되고 메모리에 바이트 배열로 저장되어야 합니다. 비밀번호가 사용되는 경우 적절한 비밀번호 기반 키 파생 함수를 통해 키로 변환되어야 합니다.
  • 암호화 무작위성이 적절하게 사용되도록 하고 예측 가능한 방식이나 낮은 엔트로피로 시드되지 않도록 하세요. 대부분의 최신 API는 보안을 위해 개발자가 CSPRNG를 시드할 필요가 없습니다.
  • MD5, SHA1, PKCS 번호 1 v1.5와 같은 폐기된 암호화 함수 및 패딩 체계를 피하세요.
  • 구성 및 설정의 효과를 독립적으로 검증하세요.

공격 시나리오

시나리오 #1: 애플리케이션이 자동 데이터베이스 암호화를 사용하여 데이터베이스에서 신용카드 번호를 암호화합니다. 그러나 이 데이터는 검색 시 자동으로 복호화되므로 SQL 주입 결함을 통해 신용카드 번호를 평문으로 검색할 수 있습니다.

시나리오 #2: 사이트가 모든 페이지에 TLS를 사용하거나 시행하지 않거나 약한 암호화를 지원합니다. 공격자는 네트워크 트래픽을 모니터링(예: 안전하지 않은 무선 네트워크에서), HTTPS에서 HTTP로 연결을 다운그레이드하고 요청을 가로채서 사용자의 세션 쿠키를 훔칩니다. 공격자는 이 쿠키를 재생하고 사용자의 (인증된) 세션을 하이재킹하여 사용자의 개인 데이터에 액세스하거나 수정합니다. 위 대신에 전송된 모든 데이터를 변경할 수 있습니다, 예를 들어 돈 이체의 수령인.

시나리오 #3: 비밀번호 데이터베이스가 모든 사람의 비밀번호를 저장하기 위해 솔트 없는 또는 간단한 해시를 사용합니다. 파일 업로드 결함이 공격자가 비밀번호 데이터베이스를 검색할 수 있도록 허용합니다. 모든 솔트 없는 해시는 미리 계산된 해시의 레인보우 테이블로 노출될 수 있습니다. 솔트된 경우에도 간단하거나 빠른 해시 함수로 생성된 해시는 GPU로 크래킹될 수 있습니다.

A03:2021 – Injection

설명

응용 프로그램이 다음과 같은 경우 공격에 취약합니다:

  • 사용자 공급 데이터가 애플리케이션에 의해 검증, 필터링 또는 정제되지 않습니다.
  • 컨텍스트 인식 이스케이핑 없이 동적 쿼리 또는 매개변수화되지 않은 호출이 인터프리터에 직접 사용됩니다.
  • 적대적 데이터가 객체-관계 매핑(ORM) 검색 매개변수 내에서 추가 민감한 레코드를 추출하는 데 사용됩니다.
  • 적대적 데이터가 직접 사용되거나 연결됩니다. SQL 또는 명령은 동적 쿼리, 명령 또는 저장 프로시저에서 구조와 악의적 데이터를 포함합니다.

더 일반적인 주입으로는 SQL, NoSQL, OS 명령, 객체 관계 매핑(ORM), LDAP, 표현 언어(EL) 또는 객체 그래프 탐색 라이브러리(OGNL) 주입이 있습니다. 개념은 모든 인터프리터에서 동일합니다. 소스 코드 검토가 애플리케이션이 주입에 취약한지 감지하는 최상의 방법입니다. 모든 매개변수, 헤더, URL, 쿠키, JSON, SOAP 및 XML 데이터 입력에 대한 자동화된 테스트가 강력하게 권장됩니다. 조직은 정적(SAST), 동적(DAST) 및 상호작용(IAST) 애플리케이션 보안 테스트 도구를 CI/CD 파이프라인에 포함하여 프로덕션 배포 전에 도입된 주입 결함을 식별할 수 있습니다.

예방 방법

주입 방지는 데이터와 명령 및 쿼리를 분리하는 것을 요구합니다:

  • 선호되는 옵션은 인터프리터를 완전히 피하는 안전한 API를 사용하거나 매개변수화된 인터페이스를 제공하거나 객체 관계 매핑 도구(ORM)로 마이그레이션하는 것입니다. 참고: 매개변수화된 경우에도 저장 프로시저가 PL/SQL 또는 T-SQL이 쿼리와 데이터를 연결하거나 EXECUTE IMMEDIATE 또는 exec()로 적대적 데이터를 실행하는 경우 SQL 주입을 도입할 수 있습니다.
  • 긍정적인 서버 측 입력 검증을 사용하세요. 이는 완전한 방어가 아니며 많은 애플리케이션이 텍스트 영역이나 모바일 애플리케이션용 API와 같은 특수 문자를 요구하기 때문입니다.
  • 잔여 동적 쿼리의 경우 특정 인터프리터에 대한 특정 이스케이프 구문을 사용하여 특수 문자를 이스케이프하세요. 참고: 테이블 이름, 열 이름 등과 같은 SQL 구조는 이스케이프될 수 없으며 따라서 사용자 공급 구조 이름은 위험합니다. 이는 보고서 작성 소프트웨어의 일반적인 문제입니다.

공격 시나리오

시나리오 #1: 애플리케이션이 다음 취약한 SQL 호출 구성에서 신뢰할 수 없는 데이터를 사용합니다:

String query = "SELECT * FROM accounts WHERE custID='" + request.getParameter("id") + "'";

시나리오 #2: 마찬가지로, 프레임워크에 대한 애플리케이션의 맹목적 신뢰는 여전히 취약한 쿼리로 이어질 수 있습니다(예: Hibernate Query Language (HQL)):

Query HQLQuery = session.createQuery("FROM accounts WHERE custID='" + request.getParameter("id") + "'");

두 경우 모두 공격자는 브라우저에서 'id' 매개변수 값을 수정하여 ' UNION SLEEP(10);--를 보냅니다. 예를 들어:

http://example.com/app/accountView?id=' UNION SELECT SLEEP(10);--

이는 두 쿼리의 의미를 accounts 테이블의 모든 레코드를 반환하도록 변경합니다. 더 위험한 공격은 데이터를 수정하거나 삭제하거나 저장 프로시저를 호출할 수 있습니다.

A04:2021 – Insecure Design

설명

안전하지 않은 설계는 "누락되거나 비효과적인 제어 설계"로 표현되는 다양한 취약점을 나타내는 광범위한 카테고리입니다. 안전하지 않은 설계는 다른 모든 Top 10 위험 카테고리의 근원이 아닙니다. 안전하지 않은 설계와 안전하지 않은 구현 사이에는 차이가 있습니다. 우리는 설계 결함과 구현 결함을 구분하는 이유가 있습니다. 그것들은 다른 근본 원인과 해결 방법을 가지고 있습니다. 안전한 설계는 여전히 악용될 수 있는 취약점으로 이어지는 구현 결함을 가질 수 있습니다. 안전하지 않은 설계는 정의상 특정 공격에 대해 방어할 필요한 보안 제어가 생성되지 않았으므로 완벽한 구현으로 수정될 수 없습니다. 안전하지 않은 설계에 기여하는 요인 중 하나는 개발 중인 소프트웨어 또는 시스템에 내재된 비즈니스 위험 프로파일링의 부족이며, 따라서 필요한 보안 설계 수준을 결정하는 실패입니다.

예방 방법

  • 보안 및 개인 정보 보호 관련 제어를 평가하고 설계하는 데 도움이 되는 AppSec 전문가와 함께 안전한 개발 수명 주기를 수립하고 사용하세요
  • 안전한 설계 패턴 라이브러리를 수립하고 사용하거나 즉시 사용할 수 있는 포장된 도로 구성 요소
  • 중요한 인증, 접근 제어, 비즈니스 로직 및 주요 흐름에 대해 위협 모델링을 사용하세요
  • 사용자 스토리에 보안 언어와 제어를 통합하세요
  • 애플리케이션의 각 계층(프론트엔드에서 백엔드로)에서 타당성 검사를 통합하세요
  • 모든 중요한 흐름이 위협 모델에 저항하는지 검증하기 위해 단위 및 통합 테스트를 작성하세요. 애플리케이션의 각 계층에 대한 사용 사례와 오용 사례를 컴파일하세요.
  • 노출 및 보호 요구 사항에 따라 시스템 및 네트워크 계층에서 계층을 분리하세요
  • 모든 계층에서 설계에 따라 테넛트를 강력하게 분리하세요
  • 사용자 또는 서비스별로 리소스 소비를 제한하세요

공격 시나리오

시나리오 #1: 자격 증명 복구 워크플로우는 NIST 800-63b, OWASP ASVS 및 OWASP Top 10에서 금지하는 "질문과 답변"을 포함할 수 있습니다. 질문과 답변은 하나 이상의 사람이 답변을 알 수 있으므로 신원 증거로 신뢰할 수 없으며, 그래서 금지됩니다. 그러한 코드는 제거되고 더 안전한 설계로 교체되어야 합니다.

시나리오 #2: 영화 체인은 그룹 예약 할인을 허용하고 보증금을 요구하기 전에 최대 15명의 참석자를 가집니다. 공격자는 이 흐름을 위협 모델링하고 몇 번의 요청으로 600개의 좌석과 모든 영화관을 한 번에 예약할 수 있는지 테스트하여 막대한 수입 손실을 유발할 수 있습니다.

시나리오 #3: 소매 체인의 전자상거래 웹사이트는 스캘퍼가 고급 비디오 카드를 구매하여 경매 웹사이트에 재판매하는 봇에 대한 보호가 없습니다. 이는 비디오 카드 제조업체와 소매 체인 소유주에게 끔찍한 홍보를 만들고 열광자들이 어떤 가격으로도 카드를 얻을 수 없어 지속적인 악감정을 만듭니다. 가용성 내 몇 초 내에 이루어진 구매와 같은 신중한 안티봇 설계와 도메인 로직 규칙은 비진정한 구매를 식별하고 그러한 거래를 거부할 수 있습니다.

A05:2021 – Security Misconfiguration

설명

애플리케이션이 다음과 같은 경우 취약할 수 있습니다:

  • 애플리케이션 스택의 어느 부분에서든 적절한 보안 강화가 누락되거나 클라우드 서비스의 권한이 잘못 구성되었습니다.
  • 불필요한 기능이 활성화되거나 설치되었습니다(예: 불필요한 포트, 서비스, 페이지, 계정 또는 권한).
  • 기본 계정과 비밀번호가 여전히 활성화되고 변경되지 않았습니다.
  • 오류 처리가 스택 추적 또는 사용자에게 과도하게 유익한 오류 메시지를 공개합니다.
  • 업그레이드된 시스템의 경우 최신 보안 기능이 비활성화되거나 안전하게 구성되지 않았습니다.
  • 애플리케이션 서버, 애플리케이션 프레임워크(예: Struts, Spring, ASP.NET), 라이브러리, 데이터베이스 등의 보안 설정이 안전한 값으로 설정되지 않았습니다.
  • 서버가 보안 헤더 또는 지시문을 보내지 않거나 안전한 값으로 설정되지 않았습니다.
  • 소프트웨어가 구식이거나 취약합니다(A06:2021-취약하고 구식 구성 요소 참조).

협력적이고 반복 가능한 애플리케이션 보안 구성 프로세스 없이는 시스템이 더 높은 위험에 처합니다.

예방 방법

다음을 포함하여 안전한 설치 프로세스가 구현되어야 합니다:

  • 반복 가능한 강화 프로세스는 적절하게 잠긴 다른 환경을 배포하는 것을 빠르고 쉽게 만듭니다. 개발, QA 및 프로덕션 환경은 모두 동일하게 구성되어야 하며 각 환경에서 다른 자격 증명을 사용합니다. 이 프로세스는 새로운 안전한 환경을 설정하는 데 필요한 노력을 최소화하기 위해 자동화되어야 합니다.
  • 불필요한 기능, 구성 요소, 문서 및 샘플이 없는 최소 플랫폼. 사용되지 않은 기능과 프레임워크를 제거하거나 설치하지 마세요.
  • 패치 관리 프로세스의 일부로 모든 보안 메모, 업데이트 및 패치에 적절한 구성을 검토하고 업데이트하는 작업(A06:2021-취약하고 구식 구성 요소 참조). 클라우드 저장소 권한을 검토하세요(예: S3 버킷 권한).
  • 분할, 컨테이너화 또는 클라우드 보안 그룹(ACL)을 통해 구성 요소 또는 테넛트 간의 효과적이고 안전한 분리를 제공하는 분할된 애플리케이션 아키텍처.
  • 클라이언트에게 보안 지시문을 전송합니다, 예: 보안 헤더.
  • 모든 환경에서 구성 및 설정의 효과를 검증하는 자동화된 프로세스.

공격 시나리오

시나리오 #1: 애플리케이션 서버는 프로덕션 서버에서 제거되지 않은 샘플 애플리케이션과 함께 제공됩니다. 이러한 샘플 애플리케이션에는 공격자가 서버를 손상시키는 데 사용하는 알려진 보안 결함이 있습니다. 이러한 애플리케이션 중 하나가 관리 콘솔이고 기본 계정이 변경되지 않았다고 가정하면 공격자는 기본 비밀번호로 로그인하고 인수합니다.

시나리오 #2: 서버에서 디렉터리 목록이 비활성화되지 않았습니다. 공격자는 단순히 디렉터리를 나열할 수 있음을 발견합니다. 공격자는 컴파일된 Java 클래스를 찾아 다운로드하고 이를 디컴파일하여 코드를 보고 역공학합니다. 공격자는 애플리케이션에서 심각한 접근 제어 결함을 찾습니다.

시나리오 #3: 애플리케이션 서버의 구성은 스택 추적과 같은 자세한 오류 메시지를 사용자에게 반환하도록 허용합니다. 이는 민감한 정보 또는 알려진 취약한 구성 요소 버전과 같은 기본 결함을 잠재적으로 노출합니다.

시나리오 #4: 클라우드 서비스 제공자(CSP)는 다른 CSP 사용자가 인터넷에 공개하는 기본 공유 권한을 가지고 있습니다. 이는 클라우드 저장소 내에 저장된 민감한 데이터에 액세스할 수 있도록 합니다.

A06:2021 – Vulnerable and Outdated Components

설명

다음과 같은 경우 취약할 수 있습니다:

  • 사용하는 모든 구성 요소의 버전을 모르는 경우(클라이언트 측 및 서버 측 모두). 여기에는 직접 사용하는 구성 요소와 중첩된 종속성이 포함됩니다.
  • 소프트웨어가 취약하거나 지원되지 않거나 구식인 경우. 여기에는 OS, 웹/애플리케이션 서버, 데이터베이스 관리 시스템(DBMS), 애플리케이션, API 및 모든 구성 요소, 런타임 환경 및 라이브러리가 포함됩니다.
  • 취약점을 정기적으로 스캔하지 않고 사용하는 구성 요소와 관련된 보안 게시판을 구독하지 않는 경우.
  • 기본 플랫폼, 프레임워크 및 종속성을 위험 기반으로 시기적절하게 수정하거나 업그레이드하지 않는 경우. 이는 패칭이 변경 제어 하에 월별 또는 분기별 작업인 환경에서 일반적으로 발생하며, 조직을 수정된 취약점에 불필요하게 노출시키는 날 또는 달을 남깁니다.
  • 소프트웨어 개발자가 업데이트된, 업그레이드된 또는 패치된 라이브러리의 호환성을 테스트하지 않는 경우.
  • 구성 요소의 구성을 안전하게 하지 않는 경우(A05:2021-보안 잘못 구성 참조).

예방 방법

다음을 위해 패치 관리 프로세스가 마련되어야 합니다:

  • 사용되지 않은 종속성, 불필요한 기능, 구성 요소, 파일 및 문서를 제거합니다.
  • 버전, OWASP Dependency Check, retire.js 등과 같은 도구를 사용하여 클라이언트 측 및 서버 측 구성 요소(예: 프레임워크, 라이브러리) 및 종속성의 버전을 지속적으로 인벤토리합니다. 구성 요소의 취약점에 대해 CVE(Common Vulnerability and Exposures) 및 NVD(National Vulnerability Database)와 같은 소스를 지속적으로 모니터링합니다. 프로세스를 자동화하기 위해 소프트웨어 구성 분석 도구를 사용합니다. 사용하는 구성 요소와 관련된 보안 취약점에 대한 이메일 알림을 구독합니다.
  • 안전한 링크를 통해 공식 소스에서만 구성 요소를 얻습니다. 수정된 악의적 구성 요소를 포함할 가능성을 줄이기 위해 서명된 패키지를 선호합니다(A08:2021-소프트웨어 및 데이터 무결성 실패 참조).
  • 유지보수되지 않거나 이전 버전에 대한 보안 패치를 생성하지 않는 라이브러리 및 구성 요소를 모니터링합니다. 패칭이 불가능한 경우 발견된 문제를 모니터링, 감지 또는 보호하기 위해 가상 패치를 배포하는 것을 고려합니다.

모든 조직은 애플리케이션 또는 포트폴리오의 수명 동안 모니터링, 분류 및 업데이트 또는 구성 변경 적용을 위한 지속적인 계획을 보장해야 합니다.

공격 시나리오

시나리오 #1: 구성 요소는 일반적으로 애플리케이션 자체와 동일한 권한으로 실행되므로 모든 구성 요소의 결함이 심각한 영향을 초래할 수 있습니다. 그러한 결함은 우발적(예: 코딩 오류) 또는 의도적(예: 구성 요소의 백도어)일 수 있습니다. 발견된 일부 악용 가능한 구성 요소 취약점의 예:

  • CVE-2017-5638, 서버에서 임의 코드 실행을 가능하게 하는 Struts 2 원격 코드 실행 취약점은 중요한 침해에 책임이 있습니다.
  • IoT(사물 인터넷)는 패칭이 자주 어렵거나 불가능하지만 패칭의 중요성은 클 수 있습니다(예: 생체 의료 장치).

공격자가 패치되지 않거나 잘못 구성된 시스템을 찾는 데 도움이 되는 자동화된 도구가 있습니다. 예를 들어 Shodan IoT 검색 엔진은 2014년 4월에 패치된 Heartbleed 취약점으로 여전히 고통받는 장치를 찾는 데 도움이 됩니다.

A07:2021 – Identification and Authentication Failures

설명

사용자 신원 확인, 인증 및 세션 관리는 인증 관련 공격으로부터 보호하기 위해 매우 중요합니다. 애플리케이션이 다음과 같은 경우 인증 약점이 있을 수 있습니다:

  • 공격자가 유효한 사용자 이름과 비밀번호 목록을 가진 자격 증명 채우기와 같은 자동화된 공격을 허용합니다.
  • 무차별 대입 또는 기타 자동화된 공격을 허용합니다.
  • "Password1" 또는 "admin/admin"과 같은 기본, 약한 또는 잘 알려진 비밀번호를 허용합니다.
  • 안전하게 만들 수 없는 "지식 기반 답변"과 같은 약한 또는 비효과적인 자격 증명 복구 및 잊어버린 비밀번호 프로세스를 사용합니다.
  • 평문, 암호화 또는 약하게 해시된 비밀번호 데이터 저장소를 사용합니다(A02:2021-암호화 실패 참조).
  • 누락되거나 비효과적인 다중 인증을 가지고 있습니다.
  • URL에 세션 식별자를 노출합니다.
  • 성공적인 로그인 후 세션 식별자를 재사용합니다.
  • 세션 ID를 올바르게 무효화하지 않습니다. 사용자 세션 또는 인증 토큰(주로 싱글 사인온(SSO) 토큰)은 로그아웃 또는 비활동 기간 동안 제대로 무효화되지 않습니다.

예방 방법

  • 가능한 경우 자동화된 자격 증명 채우기, 무차별 대입 및 도난된 자격 증명 재사용 공격을 방지하기 위해 다중 인증을 구현하세요.
  • 특히 관리자 사용자에 대해 기본 자격 증명으로 배송하거나 배포하지 마세요.
  • 상위 10,000개 최악의 비밀번호 목록에 대해 새 또는 변경된 비밀번호를 테스트하는 것과 같은 약한 비밀번호 검사를 구현하세요.
  • 기억된 비밀에 대한 NIST 800-63b의 섹션 5.1.1 지침 또는 기타 현대적 증거 기반 비밀번호 정책에 비밀번호 길이, 복잡성 및 회전 정책을 맞추세요.
  • 모든 결과에 대해 동일한 메시지를 사용하여 등록, 자격 증명 복구 및 API 경로가 계정 열거 공격에 대해 강화되도록 하세요.
  • 실패한 로그인 시도를 제한하거나 점진적으로 지연시키되 서비스 거부 시나리오를 생성하지 않도록 주의하세요. 모든 실패를 로그하고 자격 증명 채우기, 무차별 대입 또는 기타 공격이 감지되면 관리자에게 경고하세요.
  • 로그인 후 높은 엔트로피로 새로운 무작위 세션 ID를 생성하는 서버 측, 안전한 내장 세션 관리자를 사용하세요. 세션 식별자는 URL에 없어야 하며 안전하게 저장되고 로그아웃, 유휴 및 절대 타임아웃 후 무효화되어야 합니다.

공격 시나리오

시나리오 #1: 알려진 비밀번호 목록 사용인 자격 증명 채우기는 일반적인 공격입니다. 애플리케이션이 자동화된 위협 또는 자격 증명 채우기 보호를 구현하지 않는다고 가정하면 애플리케이션이 자격 증명이 유효한지 결정하기 위한 비밀번호 오라클로 사용될 수 있습니다.

시나리오 #2: 대부분의 인증 공격은 비밀번호를 유일한 요소로 계속 사용하는 것으로 인해 발생합니다. 한때 모범 사례로 간주되었던 비밀번호 회전과 복잡성 요구사항은 사용자가 약한 비밀번호를 사용하고 재사용하도록 장려합니다. NIST 800-63에 따라 조직은 이러한 관행을 중단하고 다중 인증을 사용하는 것이 권장됩니다.

시나리오 #3: 애플리케이션 세션 타임아웃이 올바르게 설정되지 않았습니다. 사용자가 공용 컴퓨터를 사용하여 애플리케이션에 액세스합니다. "로그아웃"을 선택하는 대신 사용자는 단순히 브라우저 탭을 닫고 떠납니다. 공격자는 한 시간 후 같은 브라우저를 사용하며 사용자는 여전히 인증되어 있습니다.

A08:2021 – Software and Data Integrity Failures

설명

소프트웨어 및 데이터 무결성 실패는 무결성 위반으로부터 보호하지 않는 코드 및 인프라와 관련됩니다. 이에 대한 예는 애플리케이션이 신뢰할 수 없는 출처, 저장소 및 콘텐츠 전송 네트워크(CDN)의 플러그인, 라이브러리 또는 모듈에 의존하는 경우입니다. 안전하지 않은 CI/CD 파이프라인은 무단 액세스, 악의적 코드 또는 시스템 손상의 잠재력을 도입할 수 있습니다. 마지막으로, 많은 애플리케이션은 이제 자동 업데이트 기능을 포함하며, 업데이트가 충분한 무결성 검증 없이 다운로드되고 이전에 신뢰된 애플리케이션에 적용됩니다. 공격자는 잠재적으로 자신의 업데이트를 업로드하여 모든 설치에 배포되고 실행될 수 있습니다. 또 다른 예는 공격자가 보고 수정할 수 있는 구조로 객체 또는 데이터가 인코딩 또는 직렬화되는 경우 안전하지 않은 역직렬화에 취약합니다.

예방 방법

  • 소프트웨어 또는 데이터가 예상 출처에서 왔고 변경되지 않았음을 검증하기 위해 디지털 서명 또는 유사한 메커니즘을 사용하세요.
  • npm 또는 Maven과 같은 라이브러리 및 종속성이 신뢰할 수 있는 저장소를 소비하도록 하세요. 더 높은 위험 프로필이 있는 경우 검증된 내부 알려진 좋은 저장소를 호스팅하는 것을 고려하세요.
  • OWASP Dependency Check 또는 OWASP CycloneDX와 같은 소프트웨어 공급망 보안 도구가 구성 요소에 알려진 취약점이 없는지 검증하는 데 사용되도록 하세요.
  • 악의적 코드 또는 구성이 소프트웨어 파이프라인에 도입될 가능성을 최소화하기 위해 코드 및 구성 변경에 대한 검토 프로세스가 있는지 확인하세요.
  • 빌드 및 배포 프로세스를 통해 흐르는 코드의 무결성을 보장하기 위해 CI/CD 파이프라인이 적절한 분리, 구성 및 액세스 제어를 가지고 있는지 확인하세요.
  • 서명되지 않거나 암호화되지 않은 직렬화된 데이터가 변조 또는 직렬화된 데이터의 재생을 감지하기 위한 일부 형태의 무결성 검사 또는 디지털 서명 없이 신뢰할 수 없는 클라이언트에게 전송되지 않도록 하세요.

공격 시나리오

시나리오 #1: 서명 없는 업데이트: 많은 홈 라우터, 셋톱 박스, 장치 펌웨어 등이 서명된 펌웨어를 통해 업데이트를 검증하지 않습니다. 서명되지 않은 펌웨어는 공격자의 성장하는 목표이며 더 나빠질 것으로 예상됩니다. 이는 미래 버전에서 수정하고 이전 버전이 노화될 때까지 기다리는 것 외에 수정 메커니즘이 없는 경우가 많기 때문에 주요 관심사입니다.

시나리오 #2: SolarWinds 악의적 업데이트: 국가들은 업데이트 메커니즘을 공격하는 것으로 알려져 있으며, 최근 주목할 만한 공격은 SolarWinds Orion 공격입니다. 소프트웨어를 개발하는 회사는 안전한 빌드 및 업데이트 무결성 프로세스를 가지고 있었지만, 이러한 프로세스는 전복될 수 있었고, 몇 달 동안 회사는 18,000개 이상의 조직에 고도로 표적화된 악의적 업데이트를 배포했으며, 그 중 약 100개가 영향을 받았습니다. 이는 이러한 성격의 가장 광범위하고 가장 중요한 침해 중 하나입니다.

시나리오 #3: 안전하지 않은 역직렬화: React 애플리케이션이 Spring Boot 마이크로서비스 세트를 호출합니다. 기능적 프로그래머로서 그들은 코드를 불변으로 유지하려고 했습니다. 그들이 생각해낸 해결책은 사용자 상태를 직렬화하고 각 요청으로 앞뒤로 전달하는 것입니다. 공격자는 "rO0" Java 객체 서명(base64)을 발견하고 Java Serial Killer 도구를 사용하여 애플리케이션 서버에서 원격 코드 실행을 얻습니다.

A09:2021 – Security Logging and Monitoring Failures

설명

OWASP Top 10 2021로 돌아가서, 이 카테고리는 활성 침해를 감지, 확대 및 대응하는 데 도움이 됩니다. 로깅 및 모니터링 없이는 침해를 감지할 수 없습니다. 불충분한 로깅, 감지, 모니터링 및 활성 대응은 다음과 같은 경우 발생합니다:

  • 로그인, 실패한 로그인 및 고가치 거래와 같은 감사 가능한 이벤트가 기록되지 않습니다.
  • 경고 및 오류가 로그 메시지를 생성하지 않거나 부적절하거나 불분명합니다.
  • 애플리케이션 및 API의 로그가 의심스러운 활동에 대해 모니터링되지 않습니다.
  • 로그가 로컬에만 저장됩니다.
  • 적절한 경고 임계값 및 대응 확대 프로세스가 마련되지 않았거나 효과적이지 않습니다.
  • 침투 테스트 및 동적 애플리케이션 보안 테스트(DAST) 도구(예: OWASP ZAP)의 스캔이 경고를 트리거하지 않습니다.
  • 애플리케이션이 실시간 또는 거의 실시간으로 활성 공격을 감지, 확대 또는 경고할 수 없습니다.
  • 로깅 및 경고 이벤트를 사용자 또는 공격자에게 표시하여 정보 유출에 취약합니다(A01:2021-접근 제어 실패 참조).
  • 로그 데이터가 올바르게 인코딩되지 않으면 로깅 또는 모니터링 시스템에 대한 주입 또는 공격에 취약합니다.

예방 방법

개발자는 애플리케이션의 위험에 따라 다음 제어 중 일부 또는 전부를 구현해야 합니다:

  • 모든 로그인, 접근 제어 및 서버 측 입력 검증 실패가 의심스러운 또는 악의적 계정을 식별하기에 충분한 사용자 컨텍스트로 기록되고 지연된 포렌식 분석을 허용할 만큼 충분한 시간 동안 유지되도록 하세요.
  • 로그가 로그 관리 솔루션이 쉽게 소비할 수 있는 형식으로 생성되도록 하세요.
  • 로그 데이터가 로깅 또는 모니터링 시스템에 대한 주입 또는 공격을 방지하기 위해 올바르게 인코딩되도록 하세요.
  • 고가치 거래가 변조 또는 삭제를 방지하는 무결성 제어와 함께 감사 추적을 가지고 있도록 하세요, 예: 추가 전용 데이터베이스 테이블 또는 유사한 것.
  • DevSecOps 팀은 의심스러운 활동이 빠르게 감지되고 대응되도록 효과적인 모니터링과 경고를 구축해야 합니다.
  • NIST 800-61r2 또는 이후 버전과 같은 사건 대응 및 복구 계획을 수립하거나 채택하세요.

OWASP ModSecurity Core Rule Set과 같은 상업적 및 오픈 소스 애플리케이션 보호 프레임워크가 있으며, Elasticsearch, Logstash, Kibana (ELK) 스택과 같은 오픈 소스 로그 상관 소프트웨어가 사용자 정의 대시보드와 경고를 특징으로 합니다.

공격 시나리오

시나리오 #1: 아동 건강 계획 제공자의 웹사이트 운영자는 모니터링 및 로깅 부족으로 인해 침해를 감지할 수 없었습니다. 외부 당사자가 건강 계획 제공자에게 공격자가 350만 명 이상의 아동의 민감한 건강 기록 수천 개에 액세스하고 수정했다고 알렸습니다. 사건 후 검토에서 웹사이트 개발자가 중요한 취약점을 해결하지 않았음을 발견했습니다. 시스템에 로깅 및 모니터링이 없었기 때문에 데이터 침해가 2013년부터 진행 중일 수 있었으며, 7년 이상의 기간입니다.

시나리오 #2: 주요 인도 항공사가 수백만 승객의 10년 이상의 개인 데이터(여권 및 신용카드 데이터 포함)를 포함한 데이터 침해를 겪었습니다. 데이터 침해는 제3자 클라우드 호스팅 제공자에서 발생했으며, 어느 정도 시간이 지난 후 항공사에 침해를 알렸습니다.

시나리오 #3: 주요 유럽 항공사가 GDPR 보고 가능한 침해를 겪었습니다. 침해는 공격자가 400,000개 이상의 고객 결제 기록을 수확한 결제 애플리케이션 보안 취약점으로 인해 발생한 것으로 보고되었습니다. 항공사는 결과적으로 개인 정보 보호 규제 기관으로부터 2천만 파운드의 벌금을 받았습니다.

A10:2021 – Server-Side Request Forgery (SSRF)

설명

SSRF 결함은 웹 애플리케이션이 사용자 공급 URL을 검증하지 않고 원격 리소스를 가져올 때마다 발생합니다. 공격자가 방화벽, VPN 또는 다른 유형의 네트워크 액세스 제어 목록(ACL)으로 보호되는 경우에도 예상치 못한 대상으로 조작된 요청을 보내도록 애플리케이션을 강제할 수 있습니다.

현대 웹 애플리케이션이 최종 사용자에게 편리한 기능을 제공함에 따라 URL 가져오기가 일반적인 시나리오가 됩니다. 결과적으로 SSRF의 발생률이 증가하고 있습니다. 또한 클라우드 서비스와 아키텍처의 복잡성으로 인해 SSRF의 심각성이 높아지고 있습니다.

예방 방법

개발자는 다음 심층 방어 제어 중 일부 또는 전부를 구현하여 SSRF를 방지할 수 있습니다:

네트워크 계층에서
  • SSRF의 영향을 줄이기 위해 원격 리소스 액세스 기능을 별도 네트워크로 분할
  • "기본 거부" 방화벽 정책 또는 네트워크 액세스 제어 규칙을 시행하여 필수 인트라넷 트래픽을 제외한 모든 것을 차단합니다. 힌트: 애플리케이션 기반으로 방화벽 규칙의 소유권과 수명 주기를 설정합니다. 방화벽에서 모든 허용 및 차단된 네트워크 흐름을 로그합니다(A09:2021-보안 로깅 및 모니터링 실패 참조).
애플리케이션 계층에서:
  • 모든 클라이언트 공급 입력 데이터를 정리하고 검증
  • 긍정적인 허용 목록으로 URL 스키마, 포트 및 대상을 시행
  • 원본 응답을 클라이언트에게 보내지 않음
  • HTTP 리다이렉션 비활성화
  • DNS 리바인딩 및 "시간 확인, 시간 사용"(TOCTOU) 경쟁 조건과 같은 공격을 피하기 위해 URL 일관성을 인식
고려할 추가 조치:
  • 프론트 시스템에 다른 보안 관련 서비스를 배포하지 마세요(예: OpenID).
  • 이러한 시스템의 로컬 트래픽을 제어하세요(예: localhost)
  • 전용 및 관리 가능한 사용자 그룹이 있는 프론트엔드의 경우 매우 높은 보호 요구 사항을 고려하여 독립 시스템에서 네트워크 암호화(예: VPN)를 사용하세요

거부 목록 또는 정규식을 사용하여 SSRF를 완화하지 마세요. 공격자는 거부 목록을 우회하는 페이로드 목록, 도구 및 기술을 가지고 있습니다.

공격 시나리오

공격자는 웹 애플리케이션 방화벽, 방화벽 또는 네트워크 ACL 뒤에 보호된 시스템을 공격하기 위해 SSRF를 사용할 수 있으며, 다음과 같은 시나리오를 사용합니다:

시나리오 #1: 내부 서버 포트 스캔 – 네트워크 아키텍처가 분할되지 않은 경우 공격자는 내부 네트워크를 매핑하고 SSRF 페이로드 연결의 연결 결과 또는 연결 또는 거부에 소요된 시간에서 내부 서버의 포트가 열려 있는지 닫혀 있는지 결정할 수 있습니다.

시나리오 #2: 민감한 데이터 노출 – 공격자는 로컬 파일 또는 내부 서비스에 액세스하여 민감한 정보를 얻을 수 있습니다.

file:///etc/passwd
http://localhost:28017/

시나리오 #3: 클라우드 서비스의 메타데이터 저장소 액세스 – 대부분의 클라우드 제공자는 다음과 같은 메타데이터 저장소를 가지고 있습니다. 공격자는 메타데이터를 읽어 민감한 정보를 얻을 수 있습니다.

http://169.254.169.254/

시나리오 #4: 내부 서비스 손상 – 공격자는 내부 서비스를 악용하여 원격 코드 실행(RCE) 또는 서비스 거부(DoS)와 같은 추가 공격을 수행할 수 있습니다.
